# `@warraq/desktop` — Tauri 2 shell

The desktop host for macOS and Windows (Linux builds too, it is just not in CI yet). It is deliberately thin:
the whole product surface is `@warraq/ui`, served from the web host's build (`apps/web/dist`). The Rust side
adds only what a browser cannot do — native file dialogs, reads limited to the files the user picked, OS
drag-and-drop, and commands into the **natively linked** `warraq-core` (the same crate the web and extension
hosts run as WASM: one core, two builds).

On the desktop the whole core API runs natively and pages are rasterized by **PDFium**; browsers keep the
pure-Rust renderer. See [Rendering engine](#rendering-engine-pdfium-on-the-desktop) below.

```
apps/desktop/
├── icon.svg                 # original artwork; source of every icon below
├── package.json             # dev / build / icons scripts (Tauri CLI)
└── src-tauri/
    ├── Cargo.toml           # tauri 2, plugins, warraq-core (path, feature `pdfium`)
    ├── .cargo/config.toml   # macOS linker override (Xcode licence workaround)
    ├── tauri.conf.json      # window, CSP, bundle targets, resources, frontendDist
    ├── tauri.macos.conf.json  # macOS-only bundle resources (libpdfium.dylib)
    ├── capabilities/default.json
    ├── icons/               # generated by `pnpm --filter @warraq/desktop icons`
    ├── resources/pdfium/    # libpdfium.dylib + LICENSE + licenses/ (bundled)
    ├── tests/core_bridge.rs # the registry against the Arabic corpus, with PDFium
    └── src/
        ├── lib.rs           # host commands and the file-drop forwarder
        └── core_bridge.rs   # doc_* commands over the in-process document registry
```

## Prerequisites

- Rust stable (`rust-toolchain.toml` at the repo root pins the channel; `rustup` installs it on first use)
- Node 22 and pnpm (`packageManager` in the root `package.json`; `corepack enable` or `npm i -g pnpm`)
- wasm-pack (the web UI embeds the WASM core: `pnpm build:core`)
- macOS: Xcode Command Line Tools. Windows: Visual Studio Build Tools (C++ workload) and the WebView2 runtime.
  Linux: `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf`.

## Run and build

```bash
pnpm install
pnpm build:core                             # WASM core for the web UI (optional: the UI falls back to a mock core)
pnpm --filter @warraq/desktop dev           # tauri dev: starts `pnpm --filter @warraq/web dev` (port 5173) and opens the window
pnpm --filter @warraq/desktop build         # tauri build: runs `pnpm --filter @warraq/web build`, compiles, bundles (unsigned)
pnpm --filter @warraq/desktop icons         # regenerate src-tauri/icons from icon.svg
```

`tauri build` output (`apps/desktop/src-tauri/target/release/`):

| Platform | Files                                                                                     |
| -------- | ----------------------------------------------------------------------------------------- |
| macOS    | `bundle/macos/Warraq.app`, `bundle/dmg/Warraq_<version>_<arch>.dmg`                       |
| Windows  | `bundle/msi/Warraq_<version>_x64_en-US.msi`, `bundle/nsis/Warraq_<version>_x64-setup.exe` |
| Linux    | `bundle/deb`, `bundle/rpm`, `bundle/appimage`                                             |

To build only some bundles: `pnpm --filter @warraq/desktop build -- --bundles app dmg`.

Note on paths: Tauri resolves `build.frontendDist` relative to `src-tauri/`, so the config says `../../web/dist`,
which is `apps/web/dist` at the repository level.

## Host API (what the UI can call)

Invoked with `@tauri-apps/api` (`withGlobalTauri` is off; nothing is exposed on `window`).

**Adapter selection.** `@warraq/ui` picks its host at runtime, in `packages/ui/src/core/client.ts`: if
`window.__TAURI_INTERNALS__` exists, `CoreClient` routes every request through
`packages/ui/src/core/host-tauri.ts` (these commands) and starts no Web Worker at all; in a browser it keeps
the WASM worker, unchanged. The adapter calls `window.__TAURI_INTERNALS__.invoke` directly — that object is
injected even with `withGlobalTauri: false`, and going through it keeps `@warraq/ui` free of a
`@tauri-apps/api` dependency that the web and extension builds would otherwise have to carry. `?core=mock`
still forces the mock core on the desktop too.

|                                                           |                                                                                                                                                                 |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `invoke("core_version")` → `string`                       | `warraq_core::version()` of the natively linked core                                                                                                            |
| `invoke("core_engine")` → `string`                        | the rasterizer actually in use: `"pdfium+hayro"`, or `"hayro"` if the dynamic library could not be loaded                                                       |
| `doc_*` commands                                          | the whole of `packages/core/API.md` over a native document registry — see [the core bridge](#the-core-bridge-doc_-commands)                                     |
| `invoke("read_file_bytes", { path })` → `ArrayBuffer`     | the file's bytes as a raw IPC response (no JSON array). Refused with `E_SCOPE …` unless the path came from the dialog plugin or a drop; `E_IO …` on read errors |
| `open()` / `save()` from `@tauri-apps/plugin-dialog`      | native dialogs; every picked path is added to the fs scope at runtime                                                                                           |
| `readFile()` / `writeFile()` from `@tauri-apps/plugin-fs` | allowed only for paths in that scope (`fs:allow-read-file`, `fs:allow-write-file`; no static scope entries)                                                     |
| event `warraq://file-drop`, payload `{ paths: string[] }` | emitted after the Rust side allowed the dropped files in the fs scope. Tauri's own `tauri://drag-enter/over/leave/drop` events still fire for hover UI          |

Capabilities are in `src-tauri/capabilities/default.json` (`core:default`, `dialog:allow-open/save/message/ask/confirm`,
`fs:allow-read-file`, `fs:allow-write-file`). There is no static fs scope: the only readable files are the ones
the user picked in a dialog or dropped on the window. The `doc_*` and `core_*` commands are this app's own
commands, so they need no capability entry; only plugin commands do.

### The core bridge (`doc_*` commands)

`src-tauri/src/core_bridge.rs` puts the whole of `packages/core/API.md` behind Tauri commands, over an
in-process registry of open documents. Handles are `u32`; errors are strings with the same stable prefixes as
the WASM build (`E_PARSE`, `E_PASSWORD`, `E_RENDER`, `E_NOT_FOUND`).

| Command                                                 | Notes                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `doc_open` → `u32`                                      | the PDF arrives as the **raw request body** (`invoke("doc_open", arrayBuffer)`), never as a JSON array of numbers. An optional password rides in the `x-warraq-password-hex` header, hex-encoded UTF-8, because header values must be ASCII and passwords may be Arabic |
| `doc_close(handle)` → `bool`                            | drops the document; closing twice is a no-op                                                                                                                                                                                                                            |
| `doc_page_count(handle)` → `u32`                        |                                                                                                                                                                                                                                                                         |
| `doc_page_size(handle, index)` → `[f32; 2]`             | points, after `/Rotate`                                                                                                                                                                                                                                                 |
| `doc_render_page(handle, index, scale)` → `ArrayBuffer` | raw body: `width` u32 LE + `height` u32 LE + RGBA8. A 2000×2800 page is ~22 MB of pixels; JSON would be ~3× that in digits                                                                                                                                              |
| `doc_extract_text(handle, index)` → `string`            | logical-order text, lines joined by `\n`                                                                                                                                                                                                                                |
| `doc_text_lines(handle, index)` → `TextLine[]`          | JSON `{text, x, y, width, height, direction}`                                                                                                                                                                                                                           |
| `doc_search(handle, query)` → `u32[]`                   | page indices, Arabic-aware normalization                                                                                                                                                                                                                                |
| `doc_metadata(handle)` → `string`                       | JSON `{title, author, producer, creator, pages, encrypted, engine}`                                                                                                                                                                                                     |

**Threading.** `warraq_core::Document` holds a `Box<dyn RenderDoc>`, a trait object with no `Send` bound, so
`Mutex<HashMap<u32, Document>>` is not `Sync` and cannot be Tauri managed state. The registry is instead owned
by one dedicated `warraq-core` thread and reached over a job channel: documents never cross a thread boundary,
calls run in arrival order, and every command is `#[tauri::command(async)]` so a long parse or render never
blocks the window's event loop.

### Rendering engine: PDFium on the desktop

ADR-0003 chose PDFium as the reference rasterizer; ADR-0006 narrowed it: **desktop and mobile use native
PDFium, while the extension and web default to the pure-Rust `hayro` backend** inside the single WASM module,
so browsers download 1.96 MB instead of an extra 2.4 MB PDFium module. The `Renderer` trait keeps both behind
one API, so this is a build/runtime flag, not a fork of the code. Text extraction, search, paragraph detection
and everything else go through the same `warraq-core` calls on every target: only the rasterizer differs.

This crate therefore depends on `warraq-core` with `features = ["pdfium"]`. At startup `core_bridge::setup`
sets `PDFIUM_LIB_DIR` to the first directory that actually holds the library:

1. `$PDFIUM_LIB_DIR`, if it is already set — **that always wins**, so you can point the app at another build:
   `PDFIUM_LIB_DIR=/path/to/lib pnpm --filter @warraq/desktop dev`
2. the bundled resource (`Warraq.app/Contents/Resources/resources/pdfium/`)
3. debug builds only: `src-tauri/resources/pdfium/`, then `.tools/pdfium/mac/lib/` at the repository root — so
   `tauri dev` works before anything has been bundled

If none of them binds, the core degrades to the pure-Rust renderer on its own; nothing crashes and
`core_engine()` reports `"hayro"` instead of `"pdfium+hayro"`. The UI shows that string in the status bar, so a
silent downgrade is visible rather than mysterious.

**Bundling and licence.** `src-tauri/resources/pdfium/` holds `libpdfium.dylib` plus the upstream `LICENSE`,
`VERSION` and the whole `licenses/` folder, and `bundle.resources` ships all of it (the dylib itself is listed
in `tauri.macos.conf.json`, so a Windows or Linux build does not look for a macOS file — drop `pdfium.dll` or
`libpdfium.so` into the same folder and add the matching platform config when those builds are wired up). The
binaries come from [bblanchon/pdfium-binaries](https://github.com/bblanchon/pdfium-binaries), build
`chromium/8057`. PDFium and everything it vendors (FreeType, libjpeg-turbo, OpenJPEG, zlib, libpng, lcms, ICU,
abseil) are BSD-3 or equally permissive — no copyleft enters the build, which is why the licence files ship
next to the library. See the root `THIRD-PARTY-NOTICES.md`.

**Verifying it.** `apps/desktop/src-tauri/tests/core_bridge.rs` drives the same registry code against
`tests/corpus/arabic/generated/chrome-cairo-mixed-invoice.pdf`: it asserts the engine is PDFium (not the
fallback), that page 1 renders 595×842 at scale 1.0 with real ink on it, and that `doc_extract_text` returns
`فاتورة ضريبية مبسطة` in logical order.

```bash
cd apps/desktop/src-tauri && cargo test          # uses the bundled or session PDFium
PDFIUM_LIB_DIR=/path/to/lib cargo test           # or point it somewhere else
```

### Content Security Policy

`tauri.conf.json` carries the web app's CSP (`default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; …;
object-src 'none'`) with one addition, `ipc: http://ipc.localhost` in `connect-src`. Those two sources are
Tauri's in-process IPC loopback (custom `ipc://localhost` scheme on macOS/Linux, `http://ipc.localhost` on
Windows), not network origins; without them Tauri's IPC falls back to `postMessage` and every binary response
(`read_file_bytes`) is JSON-encoded byte by byte. Tauri also appends the nonce/hash of its own injected scripts
at runtime. Like the web app's, `connect-src` also names the AI tool's providers — `https://api.anthropic.com`
and Ollama's port on this computer, `http://localhost:11434 http://127.0.0.1:11434` — which receive a
document's text only when the person presses Send in that tool.

## Signing and notarization — TODO

Builds are **unsigned** in Phase 1: Gatekeeper shows "cannot be opened because the developer cannot be verified"
(right-click → Open, or `xattr -d com.apple.quarantine Warraq.app`), SmartScreen warns on Windows. Nothing in CI
signs. When it is time:

**macOS** (Developer ID Application certificate + notarization)

1. Export the certificate as `.p12`; store `base64 -i cert.p12` as `APPLE_CERTIFICATE` and its password as
   `APPLE_CERTIFICATE_PASSWORD`. Tauri imports it into a temporary keychain when both are set and signs with
   `APPLE_SIGNING_IDENTITY` (or the only identity in the keychain).
2. Notarization: set `APPLE_ID`, `APPLE_PASSWORD` (an app-specific password) and `APPLE_TEAM_ID`; `tauri build`
   submits the `.app` and staples the ticket when they are present.
3. Add `"macOS": { "entitlements": … , "hardenedRuntime": true }` to `bundle` if the core ever needs JIT or
   unsigned memory (it does not today).

**Windows** (Authenticode)

1. Store the `.pfx` as base64 in `WINDOWS_CERTIFICATE` and its password in `WINDOWS_CERTIFICATE_PASSWORD`.
2. In the CI job decode it, import it (`certutil -f -p … -importPFX`), and set `bundle.windows.certificateThumbprint`
   (and `timestampUrl`, e.g. `http://timestamp.digicert.com`) — or switch to `signCommand` with Azure Trusted Signing.

**CI wiring**: the `desktop` job and `release.yml` expect exactly these repository secrets:
`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`,
`WINDOWS_CERTIFICATE`, `WINDOWS_CERTIFICATE_PASSWORD`. They are not referenced yet; see `docs/ci.md`.

## Not in Phase 1

- Sandboxed render process (`warraq-renderd`, Phase 2) — parsing and rendering run on the host's own
  `warraq-core` thread, in the app process. That is off the UI thread but not out of process yet, so a
  malicious file can still take the app down with it.
- Tiled rendering and a bitmap cache: `doc_render_page` rasterizes a whole page per call.
- Auto-update, deep links / "Open with" file associations, iOS (needs a `staticlib` of this crate; the
  `[lib]` crate types are already set for it).
