# محرر PDF for iPhone and iPad

A native SwiftUI app (iOS 18+, Swift 6 with strict concurrency, Xcode 27's
SDK), universal, with the shared Rust core linked in as an XCFramework. The
interface is SwiftUI from the first screen to the last; PDFKit draws the
pages; the core does what Apple's frameworks do not — Arabic read in
logical order from any PDF, the tool operations, the Library's index, the
incremental save that leaves the original bytes untouched.

Documents the person opens stay where they are (a security-scoped
bookmark remembers them); documents the share extension saves land in the
app's own Documents folder, which the Files app shows under the app's name.
The recents list, the last searches and the thumbnails live in the App
Group container (`group.app.warraq`), where the widgets read them.

## The Library

The index is the core's (`library.*`, `packages/core/API.md`): one file,
`Library/Application Support/Library/library.wlx` in the app's own
container, holding each document's text lines and never its bytes. Its
sources are the app's Documents folder (keys `documents/<file>`) and one
folder chosen in Files or iCloud Drive (`folder/<path inside it>`), kept as
a security-scoped bookmark in the app's defaults. A run (`LibraryIndexer`)
lists the sources with one `stat` per file, skips what has not changed
(size and date), reads a PDF's text through the core page by page, sends
pages with no text of their own — and pictures — through the OCR seam,
hands the text to `library.add`, draws a thumbnail with the core, and puts
the document into Core Spotlight (title, kind, the first 60 000 characters).
Progress and Stop are on the status line above the grid; the run stops
between files. Search (`.searchable` above the documents) is
`library.search`: Arabic matched without tashkeel and with the letter forms
unified, hits grouped by document with the page and the matched words
marked, filters for kind, tag, place, scans only and the document's own
date; a hit opens the document at its page. Tags and rules are the core's
(`library.tag`, `library.rules`), edited from the Tags section.

**The OCR seam** is `TextRecognizer.shared` (`Shared/TextRecognizer.swift`):
`recognize(image, languages) -> [RecognizedWord]`, words with boxes and a
line number. `VisionTextRecognizer` stands behind it by default; the
scanner's own pipeline can set a better one at launch. Tests drive it with a
fake.

**Routes.** Everything outside the app — widgets, the Control Center
control, Shortcuts, Siri, the Home Screen quick actions, Spotlight results —
sends it to one of `AppRoute`'s places (scan, open a document, search the
Library, the last document). Widgets use the URL form
(`pdfeditor://scan`, `pdfeditor://open/<id>`, `pdfeditor://search?q=…`);
intents post the route through the App Group's defaults, and the Library
takes it as the scene becomes active.

## Building

Everything runs on the simulator only: this Mac has no signing identity.
A device or TestFlight needs an Apple Developer team (`DEVELOPMENT_TEAM`
and `CODE_SIGN_STYLE: Automatic` in `project.yml`) — the owner's decision.

```
scripts/ios/build-core.sh        # cargo (aarch64-apple-ios, aarch64-apple-ios-sim) → Vendor/WarraqCore.xcframework
scripts/ios/build.sh             # xcodegen → build for iPhone 17 and iPad Pro 13-inch (M5) → unit + UI tests → screenshots
scripts/ios/build.sh --no-test   # generate and build only
scripts/ios/build.sh --unit      # unit tests only
scripts/ios/build.sh --iphone    # one simulator (or --ipad)
```

On the shared 8 GB Mac, run both through the queue:
`~/Developer/warraq/.tools/one-at-a-time.sh scripts/ios/build.sh`. Build the
core with a `CARGO_TARGET_DIR` of your own (the script defaults to
`apps/ios/.build/cargo`); delete it and `apps/ios/.build/DerivedData` when
you finish — disk is limited.

The scripts are what CI would run; the equivalent by hand:

```
cd apps/ios && xcodegen generate
xcodebuild -project apps/ios/PDFEditor.xcodeproj -scheme PDFEditor \
  -derivedDataPath apps/ios/.build/DerivedData \
  -destination 'platform=iOS Simulator,name=iPhone 17' build-for-testing
xcodebuild -project apps/ios/PDFEditor.xcodeproj -scheme PDFEditor \
  -derivedDataPath apps/ios/.build/DerivedData \
  -destination 'platform=iOS Simulator,name=iPhone 17' test-without-building \
  TEST_RUNNER_WARRAQ_SCREENSHOT_DIR=$PWD/docs/design/ios TEST_RUNNER_WARRAQ_DEVICE_SLUG=iPhone-17
```

## How the core is linked

- `packages/core/warraq-core/src/ffi.rs` (feature `ffi`, crate type
  `staticlib`) is the C ABI: `warraq_open`, `warraq_call`,
  `warraq_call_static`, `warraq_save`, `warraq_free` and the readers that
  mirror `wasm.rs`. JSON in and out; blobs as (pointer, length) pairs;
  errors as codes carrying the core's `E_…` names; a panic caught at the
  boundary and answered as `WARRAQ_E_PANIC`. The header is
  `packages/core/warraq-core/include/warraq_core.h` with a module map
  (`WarraqCoreFFI`); a Rust test keeps header and exports in step.
- `scripts/ios/build-core.sh` builds it with the workspace's `ios` profile
  (release, unwinding so the catch works, no cross-crate LTO because a
  thin-LTO static library is LLVM bitcode Xcode's linker cannot read) for
  the device and the simulator, and packs both with the headers into
  `Vendor/WarraqCore.xcframework`. `WARRAQ_IOS_X86=1` adds the Intel
  simulator slice; `WARRAQ_IOS_DEBUG=1` builds debug.
- `WarraqCore` is a static framework target wrapping the C module in
  `actor Core`: `Core.open(bytes:password:)`, `call(op:args:blobs:)`,
  `Core.callStatic`, `save()`, `close()`, and typed readers
  (`extractText`, `textLines`, `search`, `metadata`, `paragraphs`,
  `renderPage`, `pageSize`). Errors are `CoreError` cases. One handle,
  one thread at a time: the actor guarantees it, and every call runs off
  the main thread.
- The app, the widgets and the share extension list both the framework
  target and the XCFramework as dependencies (`embed: false`): a static
  framework's code is copied into whoever links it, and the archive's
  symbols are resolved at that link.

## Adding a screen, calling the core

- A screen is a SwiftUI view built from `Design/Theme.swift`'s tokens and
  `Design/Components.swift`; strings go through `Text("key")` and the
  String Catalog (`Resources/Localizable.xcstrings`, Arabic and English —
  the app's name inside English text is written between U+2067 and
  U+2069, `AppName.isolated`). Give controls `accessibilityIdentifier`s and
  test them in `PDFEditorUITests`.
- A UI test launches the app with its settings on the command line —
  `-language ar|en`, `-appearance light|dark` (the app's own UserDefaults
  keys), `-AppleLanguages (ar)` for the system's frameworks — and, in
  Debug builds only, `-warraqReset 1` (an empty Library first) and
  `-warraqOpen <path>` (open that file). Corpus files listed under the
  test target in `project.yml` are in the test bundle. Screenshots are
  written where `WARRAQ_SCREENSHOT_DIR` says, named
  `<screen>-<language>-<appearance>-<device>.jpg`.
- A document tool edits through `DocumentModel.apply(op, args:, blobs:,
  undoManager:)`: the core runs the operation, the model takes the new
  bytes (an incremental update on the original), PDFKit reloads, and undo
  gets a step back. `model.engine` is the `Core` actor for readers.
  Nothing touches the file until `model.save()` (Library documents) or
  the `DocumentGroup` scene saves (documents opened from outside).
- Work that needs no open document (combining, the Library's index, OCR's
  text layer, exports) is `Core.callStatic(op:args:blobs:)`.
- New sidebar sections join `LibrarySection`; new settings join
  `SettingsView`; new widgets join `WidgetsBundle`.

## What the simulator cannot do

- The real camera: VisionKit's document camera is unavailable on the
  simulator; the scanner's pipeline is proven on photos.
- Signing for a device, App Store or TestFlight: no identity here.
- Face ID: the simulator enrols a face and answers a match through
  `simctl spawn <udid> notifyutil` (`scripts/ios/build.sh` does this while
  the lock test runs); there is no real sensor.
- The real share sheet from other apps, Home Screen widgets, the Control
  Center control, Siri and Shortcuts are exercised as far as `xcodebuild
  test` and `simctl` reach: their timelines, entity queries and routes are
  tested as code, the app's handling of each route through the interface.
- The index's OCR on the simulator is Vision's, with whatever languages
  Vision offers there (`LibraryTests.testVisionLanguagesOnThisSimulator`
  prints the list; `docs/STATUS.md` records it).
